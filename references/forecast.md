# 大用量预测与八类浪费

## 大用量预测【经验规则】
粗估折算 token ≈ 读入材料量×2 + 预计输出量×4 + 预计轮数×当前上下文大小（最后一项最易漏）。这是经验估算，不是官方计费公式，只用来分档，不当作精确数字。

| 估算（折算 token） | 做法 |
|---|---|
| < 10 万 | 直接做，写预估 |
| 10 万到「提醒线」 | 拆成并行块，每块写预估；先让轻量模型抽事实包（不超过 6,000 字） |
| ≥ 提醒线（例：50 万） | 动手前告诉用户做什么、预估多少，不必等批准 |
| ≥ 确认线（例：100 万） | 先交方案（为什么这么多、先做样品、分几批），用户确认后再分批做 |

两条线由你自己定。预估不是硬停线：不要给子代理写「用到 N 万就停」，半路强停会交回没法接着用的半成品，换人接手要重读全部上下文，反而更贵；真正要停的是空转（同一动作失败第 3 次、长时间没进展）。

常见大头：整本 PDF/PPT 解析进上下文、资料库全文整篇带入、多轮推理评审、长会话第 N 轮追问、批量图片/视频生成（先确认参数和数量，先出一件）。事后记「预估 vs 实际」，连续 3 次偏差超 2 倍就调系数。

## 八类浪费对照
| 浪费 | 在 WorkBuddy 里的样子 | 怎么发现 | 对策（照着说） |
|---|---|---|---|
| 过度生产 | 需求没确认就开工；多做了没人要的版本 | 交付物用不上 | 「需求确认前先不要开发」；先出 1 件样品 |
| 等待 | 等用户拍板、等授权、后台空跑、反复查状态 | 任务长时间没有新结果 | 要决定的事用选择题问；写明卡在谁；停止轮询 |
| 搬运 | 大文件整包贴进对话；同一材料在多个代理之间来回传 | 同一份材料出现 2 次 | 直接读本地文件，只传摘要 |
| 过度加工 | 只要削皮却切成果盘：反复润色、多轮评审 | 评审到第 3 轮 | 写清「做到什么程度就停」，先给能用的 |
| 库存 | 对话越拉越长；旧版本、中间文件堆着没人用 | 上下文超过约 5 万 token | 上下文大了再交接；换任务开新对话 |
| 多余动作 | 同一文件读多遍；盲猜网址试探；简单活用最贵模型 | 一次提问工具循环超过 5 次 | 先读目录；能写脚本就写脚本；按活选模型 |
| 返工 | 方向错了重做；批量整批返工；同一错犯两次 | 同一类错出现第 2 次 | 先出样品；把错误写成规则 |
| 经验没用起来 | 好做法没沉淀，每次重新教 | 同一句话说了 3 遍 | 写进规则或技能，开工先读 |

「怎么发现」列的数字是经验阈值，按自己的实测调整。

先问「该不该做、做什么」，再问「怎么省着做」。在错的事上做效率优化，是双重浪费。

## 实测补充【环境实测】2026-11-16 单一环境
- 同一任务两次积分可差 2–4 倍；技能固定开销估计约 +5 千 token/轮（约 +16%），也有 2–4 倍波动。
- 积分按「请求」计，同一轮里并行多做几件事，比拆成多轮便宜（经验推断）。

## 评审少走弯路【实测】
同一份交付连评 4 轮，分数 58 → 66 → 74 → 66，根子是没有先定标准。
1. 先写「90 分长什么样」的评分表：维度、四档（底线、达标、优秀、杰出）、一票否决；照着做，照着评。
2. 子代理自报的结果用真实数据复核：合成数据测出召回 9/10，真实数据只有 5/7。
3. 规则冲突本身就是 bug：加新规则时删掉矛盾的旧规则；同类错第二次出现，就写成固定检查。
4. 检查脚本也会误判：页面还在加载就截图，会报「正文过短」；要等关键字出现、长度稳定后再判。
